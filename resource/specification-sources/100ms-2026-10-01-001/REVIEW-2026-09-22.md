# Specification Consistency Review — 2026-09-22

> Historical baseline, written before the authorized corrections. The findings and line numbers below describe that baseline. See [resolution status](RESOLUTION-2026-09-22.md) for the current package and validation results.

## Scope and conclusion

Reviewed all 18 use cases, 11 API specifications, 129 OCL rule blocks, the shared model, indexes, source manifest, domain context, assumptions, coverage report, and DBML schema.

The requested directory `D:\figma\_spec\100ms Video Conferencing and Live Streaming` does not exist in this environment. This review covers the matching package at `D:\figma_spec\100ms Video Conferencing and Live Streaming`.

The package has a consistent document skeleton and its DBML compiles, but it is not yet an internally complete implementation contract. Several rules contradict each other, several intended state changes are not constrained, and some APIs cannot carry the inputs or outputs required by their use cases.

This is an internal document review, not an audit against the original Figma canvas or the current 100ms service. No existing specification was changed. Findings about authorization and concurrency describe gaps in the specification; they are not claims that a deployed implementation has those vulnerabilities.

Priority: **P1** = resolve before implementing the affected flow; **P2** = resolve before accepting the package as a complete contract.

## Findings

### R01 — P1 — Host role assignment contradicts the default join role

Evidence: [UC-02](01-inception/uc/uc-02-join-a-session.md), lines 125–157, BR-UC-02-04 and BR-UC-02-07.

The first rule unconditionally assigns `VIEWER` for a live stream and `BROADCASTER` for a video conference. The second requires `HOST` when the returned participant is the designated host. For that participant, both constraints cannot hold. If the designated-host condition never holds, the specified join flow has no route to host participation.

Correction: specify one mutually exclusive role assignment, with an explicit designated-host branch and the session-kind defaults in the other branch. Define how the joining identity resolves to the designated host, since the persisted host reference is a participant ID and participation is created on join.

### R02 — P1 — Leave and end constrain the same operation with incompatible preconditions

Evidence: [UC-17](01-inception/uc/uc-17-leave-a-session.md), lines 178–192; [UC-18](01-inception/uc/uc-18-end-a-session-for-everyone.md), lines 193–198. Both use `SessionService::depart(command: DepartureCommand): Departure` and [the same API](01-inception/api/api-session-departure.md), lines 11–14.

UC-17 requires `command.kind = LEAVE`; UC-18 requires `command.kind = END`. No model-level dispatch or conditional applicability separates these constraints. Combining the package into one operation contract therefore creates incompatible requirements. UC-17 also requires the session status to remain unchanged without a `LEAVE` guard.

Correction: use distinct domain operations such as `leave` and `end`, or define guarded constraints for each command kind in one canonical operation. Guard all action-specific preconditions and postconditions, not only the enum check.

### R03 — P1 — Core state transitions and result assignments are missing from OCL

Evidence: Business Rules in [UC-02](01-inception/uc/uc-02-join-a-session.md), [UC-03](01-inception/uc/uc-03-start-a-live-stream.md), [UC-04](01-inception/uc/uc-04-stop-a-live-stream.md), [UC-06](01-inception/uc/uc-06-request-stage-access.md), [UC-07](01-inception/uc/uc-07-respond-to-a-stage-request.md), [UC-11](01-inception/uc/uc-11-share-presentation-content.md), [UC-16](01-inception/uc/uc-16-control-session-recording.md), and [UC-18](01-inception/uc/uc-18-end-a-session-for-everyone.md).

The observable flows promise results that their formal rules do not require:

- UC-02 does not require the created participant to have `JOINED` status or bind its identity, session, and display name to the command.
- UC-03/04 do not require the stream to enter `STARTING`/`LIVE` or `ENDED`.
- UC-06 has only preconditions; it does not require a created request to be `PENDING` or a cancelled request to become `CANCELLED`.
- UC-07 changes request status but never requires the accepted participant to become `STAGE_PARTICIPANT`.
- UC-11 and UC-16 do not require the returned share/recording status to match START or STOP.
- UC-18 does not require the session itself to become `ENDED`, or its version to advance.

No operation specifies how a session moves from the DB default `LOBBY` to `LIVE`, although sharing and recording require a live session. Provisioning or provider callbacks might own this transition, but that boundary is not declared.

Correction: add explicit effects and identity bindings in OCL, including asynchronous completion/failure where applicable. Declare the owner of externally driven transitions. This does not require exposing domain policy in API field validation.

### R04 — P1 — Pre-state expressions do not reliably describe the intended changes

Evidence: [UC-03](01-inception/uc/uc-03-start-a-live-stream.md), line 159; [UC-04](01-inception/uc/uc-04-stop-a-live-stream.md), lines 129–172; [UC-12](01-inception/uc/uc-12-configure-audio-and-video-devices.md), lines 109–120; [UC-13](01-inception/uc/uc-13-select-a-virtual-background.md), lines 98–110 and 134; [UC-14](01-inception/uc/uc-14-change-session-layout.md), lines 100–129; [UC-15](01-inception/uc/uc-15-pin-or-spotlight-a-participant.md), lines 123–126; [UC-17](01-inception/uc/uc-17-leave-a-session.md), lines 153, 165, 192; [UC-18](01-inception/uc/uc-18-end-a-session-for-everyone.md), lines 148–180.

Examples:

- `result.version = stream.version + 1` reads the post-state version. If result and stream are the same object, this becomes `v = v + 1`.
- UC-04 selects participants that are still `STAGE_PARTICIPANT` in the post-state and then requires them to be `VIEWER`. This merely prohibits a remaining stage participant; it does not require each former stage participant to be demoted. The recording/request cascades have the same issue.
- Forms such as `p@pre.status` and `result@pre.cameraDeviceId` do not correctly select the old property value. Use property-level pre-state access.
- `m = m@pre` does not compare all mutable fields and cannot establish that another participant's preferences were preserved.

Correction: identify the target object and pre-state collection explicitly; compare values such as `stream.version@pre`, `p.status@pre`, and each preserved preference property. Distinguish updates from creation, where the result has no previous persisted state. These corrections follow [OMG OCL 2.4, sections 7.5.14 and 11.3.1](https://www.omg.org/spec/OCL/2.4/PDF). No OCL parser or model execution engine was run in this review.

### R05 — P1 — Authentication, actor identity, and target session are not fully bound

Evidence: [shared model](01-inception/uc/shared-domain-model.md), line 23; [UC-07](01-inception/uc/uc-07-respond-to-a-stage-request.md), lines 97–110 and 130–136; [UC-12](01-inception/uc/uc-12-configure-audio-and-video-devices.md), lines 127–128; [preferences API](01-inception/api/api-preferences-update.md), lines 24 and 65–74.

`RequestContext.participantId` is declared but unused by all rules. Checking that a supplied actor ID belongs to a host/member does not establish that the authenticated caller owns that identity. This is especially visible for preferences, where the target participant is in the URL but the rules often check only that the ID is nonblank.

UC-07 checks that the host belongs to `command.sessionId`, but its pending-request lookup is by `requestId` only. For REJECT, the accepted-participant check does not apply: a host of session A and a pending request in session B can satisfy the written checks. UC-03/04 also lack an explicit binding between the selected stream and `command.sessionId`.

Correction: specify trusted principal-to-participant resolution, self-only preference ownership, result ownership, and consistent session bindings. Keep these rules in the domain model/OCL; API authorization sections can retain public outcomes.

### R06 — P1 — Preferences API cannot implement the use cases it lists

Evidence: [preferences API](01-inception/api/api-preferences-update.md), lines 80–168; [UC-14](01-inception/uc/uc-14-change-session-layout.md), lines 43–46 and 62–67; [UC-15](01-inception/uc/uc-15-pin-or-spotlight-a-participant.md), lines 57–61; [UC-12](01-inception/uc/uc-12-configure-audio-and-video-devices.md), lines 25 and 33–34.

The request has neither `focusedParticipantId` nor `sidePanel`. A client cannot specify the participant to pin/unpin or the side panel to open/close. The response contains only `layout` and `pictureInPicture`, despite UC-12/13 requiring the client to apply the returned device/background preferences.

Correction: add the missing wire fields and return the full relevant preference representation. Define how the unified PATCH maps to the separate device, background, layout, and focus operations, including combined updates.

### R07 — P1 — Preview preferences depend on a participant created only after joining

Evidence: [UC-12](01-inception/uc/uc-12-configure-audio-and-video-devices.md), lines 21 and 29–34; [UC-13](01-inception/uc/uc-13-select-a-virtual-background.md), lines 21 and 29–34; [CONTEXT](CONTEXT.md), line 25; [preferences API](01-inception/api/api-preferences-update.md), line 24; [schema](schema.dbml), line 169.

The device flow explicitly supports preview and submits a server update. Its only API requires a session participant ID and persistence requires a participant foreign key. The package says participation is created by joining. The pre-join `participantKey` from UC-01 is not mapped to a persisted participant or preview resource.

Correction: define pre-join preferences as local draft state transferred on join, or introduce a documented preview identity/resource lifecycle. Explain the corresponding behavior for anonymous users.

### R08 — P1 — Version requirements cannot be fulfilled consistently by clients

Evidence: [stream API](01-inception/api/api-live-stream-control.md), lines 91–126; [recording API](01-inception/api/api-recording-control.md), lines 90–125; [departure API](01-inception/api/api-session-departure.md), lines 91–135; [share API](01-inception/api/api-content-share-control.md), lines 112–147; [UC-11](01-inception/uc/uc-11-share-presentation-content.md), lines 177–182.

Recording and departure require client-observed versions but no API returns recording/session versions. Stream control returns a version only after a mutation; no read/join response provides the initial stream version. Share control accepts an omitted/null `expectedVersion`, yet its postcondition unconditionally calculates `expectedVersion + 1`, and never checks that the expected version equals the stored one.

Correction: provide initial/current versions through reads, join responses, or specified events. Return new versions after updates. Define create versus update version semantics and actual optimistic compare-and-update rules. A computed next version alone is not a stale-write check.

### R09 — P1 — Idempotency is asserted but replay behavior and pre-join scope are absent

Evidence: [ASSUMPTIONS](ASSUMPTIONS.md), line 14; [join API](01-inception/api/api-session-join.md), lines 49–58; [UC-02](01-inception/uc/uc-02-join-a-session.md), lines 58–64; [UC-09](01-inception/uc/uc-09-send-a-chat-message.md), lines 147–151; [schema](schema.dbml), lines 209–217; [preferences API](01-inception/api/api-preferences-update.md), lines 38–50.

Some rules only require a nonblank key; none specify replay lookup, payload conflict, or returning the original result. `JoinCommand` has no key despite its API requiring one. Persisted deduplication is keyed by an existing participant, but a join retry may arrive before the caller has received the participant ID. Preferences is a mutation without an idempotency-key header despite the blanket assumption.

Correction: define the key's scope, trusted caller identity, replay result, conflicting-payload behavior, and retention. Provide a stable identity for deduplicating join before membership creation. Either include preferences or document an explicit exception.

### R10 — P1 — Singleton and capacity rules have no specified concurrent enforcement

Evidence: [UC-02](01-inception/uc/uc-02-join-a-session.md), lines 110–122; [UC-06](01-inception/uc/uc-06-request-stage-access.md), lines 110–115; [UC-07](01-inception/uc/uc-07-respond-to-a-stage-request.md), lines 117–123; [UC-11](01-inception/uc/uc-11-share-presentation-content.md), lines 116–119; [UC-16](01-inception/uc/uc-16-control-session-recording.md), lines 125–129; [schema](schema.dbml), lines 105–108, 131, 165, 196.

The schema supplies ordinary indexes, not uniqueness constraints, for duplicate membership, pending stage requests, active shares, and active recordings. Separate requests can both observe an empty set or remaining capacity. Stage decisions have no version field or documented atomic pending-to-terminal update.

Correction: specify transaction/locking or atomic conditional-write behavior in the domain contract, and encode applicable partial unique indexes in persistence. A full unique index on `(session, participant, status)` would incorrectly prohibit multiple historical terminal requests; uniqueness must match the active/pending subset. Session/stage capacity also needs serialized enforcement rather than only a precondition count.

### R11 — P2 — Participant pagination has no usable continuation contract

Evidence: [UC-08](01-inception/uc/uc-08-view-session-participants.md), lines 69–73 and 119–128; [participant API](01-inception/api/api-participant-list.md), lines 62–112.

OCL requires a non-null `pageSize` and limits the result to it. The API exposes only an input cursor, with neither `pageSize` nor a declared server-selected value. Its response has no next cursor or completion indication. With the documented capacities exceeding the page size, clients cannot reliably retrieve the remaining participants.

Correction: specify a page-size input or an explicit domain default, return a continuation cursor and its terminal representation, and define stable ordering and session-scoped results in OCL.

### R12 — P2 — Read/event boundaries and response payloads do not cover observable flows

Evidence: [UC-03](01-inception/uc/uc-03-start-a-live-stream.md), lines 33–34; [UC-06](01-inception/uc/uc-06-request-stage-access.md), lines 25–33; [UC-07](01-inception/uc/uc-07-respond-to-a-stage-request.md), lines 33–34; [UC-09](01-inception/uc/uc-09-send-a-chat-message.md), lines 29–34; [API index](01-inception/api/README.md).

The package promises returned chat history, a request item on another client's host interface, asynchronous live status, and end-session outcomes on all clients. There is no history/list-stage-request API or event/subscription contract, and no explicit SDK boundary providing them. This is application state delivery, distinct from excluded media bytes/provider internals.

Some immediate responses also omit promised data: stage acceptance returns no participant representation; chat creation returns no normalized body or sender; join returns no role or effective media state; viewer state omits the modeled playback/publish/mute flags.

Correction: declare polling, events, or an explicit external SDK contract with the required payloads and identity mapping. Complete the endpoint representations or clearly define how returned IDs resolve to the promised data.

### R13 — P2 — Reaction examples contradict the allowed domain values

Evidence: [reaction API](01-inception/api/api-reaction-create.md), lines 79–87 and 107–113; [UC-10](01-inception/uc/uc-10-send-an-emoji-reaction.md), lines 99–105.

The API uses `CLAP` in both request and response examples. The OCL whitelist accepts only actual emoji values, including `👏`. No code-to-emoji mapping is specified, so the documented example fails the domain rule when interpreted directly.

Correction: choose canonical enum codes with an explicit mapping, or use the same emoji values throughout API, UML, OCL, examples, and client catalog.

### R14 — P2 — PATCH omission, explicit null, and persistence are not reconciled

Evidence: [preferences API](01-inception/api/api-preferences-update.md), lines 82–138; [UC-12](01-inception/uc/uc-12-configure-audio-and-video-devices.md), lines 135–138; [schema](schema.dbml), lines 177–183.

Fields are optional and nullable, but the domain commands have no way to distinguish omitted fields from explicitly cleared fields. Mapping omitted device IDs to null would invoke the clearing rule and erase unrelated selections. `layout` and `pictureInPicture` accept null while their database columns and success-response fields are non-null, with no reset/default rule. Validation text also says a present value must be a string/boolean even when null is permitted.

Correction: model field presence, retain omitted fields, and define explicit-null behavior for every nullable field. Make request validation explicitly accept null where declared. Provide defaults or disallow null for non-null persisted preferences.

### R15 — P2 — Display-name policy differs between preview, join, assumptions, and storage

Evidence: [UC-01](01-inception/uc/uc-01-review-join-preview-and-permissions.md), lines 125–129; [ASSUMPTIONS](ASSUMPTIONS.md), line 6; [UC-02](01-inception/uc/uc-02-join-a-session.md), Business Rules; [schema](schema.dbml), line 98.

Preview readiness uses a trimmed length of 1–50. Assumptions require trimming/nonempty names. Join has neither rule nor a normalized-result assignment, and persistence permits up to 160 characters. A direct API caller can satisfy the written join rules with a blank or over-preview-limit name.

Correction: establish one domain policy enforced by join and reused by preview. A wider storage column is acceptable if explicitly intentional; it is not a substitute for the missing rule. The 50-character rule is labeled `Source: Figma`, but the package provides no precise evidence for that threshold, so verify the attribution or mark it as an assumption.

### R16 — P2 — Persistent and domain representations lack mapping decisions

Evidence: [UC-02](01-inception/uc/uc-02-join-a-session.md), lines 74–84; [schema](schema.dbml), lines 94–109, 158–160; [share API](01-inception/api/api-content-share-control.md), lines 90–110; [UC-11](01-inception/uc/uc-11-share-presentation-content.md), lines 172–174.

The joined participant model contains microphone/camera state, but the participant schema does not, and no transient media-state owner is declared. Share `kind` and `sourceReference` may be absent in the request; the only source-reference rule covers PDF, while both persisted columns are mandatory. All database IDs use UUIDs, whereas public examples use prefixed opaque IDs, with no mapping stated.

Correction: declare which state is persistent versus transient/provider-owned, specify generation or requiredness of share fields by action, and document whether public IDs encode/map to internal UUIDs. Public opaque IDs do not inherently conflict with UUID storage; the missing mapping is the issue.

### R17 — P2 — API error outcomes and common response shape are incomplete

Evidence: [common contract](01-inception/api/common-contract.md), lines 19–25; success and error sections across the 11 API files; [chat API](01-inception/api/api-chat-message-create.md), lines 116–135; [reaction API](01-inception/api/api-reaction-create.md), lines 115–127.

The common success envelope includes `message`, but individual endpoints never define that field or explicitly state inheritance. Several protected endpoints omit a public authentication failure outcome. Chat/reaction can fail their documented domain rules while the only 400 trigger describes wire decoding/schema errors; no public domain-rejection outcome is specified.

Correction: explicitly inherit the common envelope and common errors, define their types/requiredness, and map domain rejection to public error outcomes without exposing hidden predicates. Avoid silently treating a wire-valid domain rejection as an authentication or technical failure.

### R18 — P2 — Policy isolation, provenance, and validation need tightening

Evidence: [join API](01-inception/api/api-session-join.md), line 153; [ASSUMPTIONS](ASSUMPTIONS.md); [package output contract](../skills/figma-to-ocl-specs/references/output-contract.md), lines 130–136; repository validator scripts.

The join API's 409 trigger duplicates session-ended and 100/1,000 capacity policy. The supplied validator reports this as a policy-isolation failure. Keep those values in the assumptions/OCL and use a protocol-level conflict trigger in the API.

The assumption register also omits several assumed choices present in OCL, including the 50-item page limit, 1,000-character chat limit, reaction whitelist, PiP/side-panel exclusion, and cascade behavior. Add stable assumption IDs and rule mappings so product decisions can be reviewed systematically.

On this machine, running the UTF-8-without-BOM validator directly under Windows PowerShell 5.1 causes parsing errors around non-ASCII characters. Running an otherwise unchanged temporary UTF-8-BOM copy with explicit UTF-8 input decoding allows its checks to execute. Declare a compatible runtime or make file encoding explicit.

The validator checks structure and regex patterns; it does not parse/type-check OCL or prove that transitions, request/response data, and database constraints agree. Its UC-to-API direction also checks API existence rather than every reverse edge. An additional manual reverse-edge check found no missing edges in this package.

## Product decisions still requiring explicit documentation

- **Host leaves without ending:** UC-17 accepts a host leaving; stream/recording controls require a joined host. Specify replacement, rejoin/recovery, prevention, or another lifecycle outcome so a running session does not lose its controller.
- **Anonymous participation:** join and viewer APIs accept an anonymous join token, while chat, stage actions, and departure declare only a bearer token. Specify whether the join token remains usable or is exchanged for a participant credential and how callers obtain that credential.
- **Pin versus spotlight:** UC-15 treats both as personal focus. This is internally consistent with its prose, but it should be an explicit product decision if spotlight is intended to affect the whole session. The review did not recheck the original Figma evidence.
- **Restart after stopping:** start requires `READY`, while stopped streams are intended to become `ENDED` and the schema permits only one stream record per session. Specify whether restart is unsupported or how a stream resets.
